# text-to-sql — Text-to-Dashboard

Type a plain-English question, get a live dashboard. An LLM agent turns the question into a
dashboard spec (1–6 panels with SQL + chart mappings), the server validates and runs each query
against a strictly read-only Postgres role on Supabase, and the frontend renders the results with
Recharts. No SQL or errors are ever shown to the end user (`?debug=1` reveals per-panel SQL).

Currently pointed at the project's live UK property-intelligence data (land registry ownership,
VOA properties, opportunities pipeline). Scripts to load and scale the Pagila sample dataset
instead live in `db/` + `scripts/` (see `PLAN.md`, including the post-execution addendum).

## Run

```bash
npm install
cp .env.example .env.local   # fill in DATABASE_URL_READONLY + OPENAI_API_KEY
npm run dev                  # http://localhost:3000
```

## How it works

- `POST /api/dashboard { question }` → one OpenAI call (Responses API, strict structured outputs)
  returns `{ spec }`; SQL is pre-checked by the guard, panel ids assigned server-side.
- `POST /api/panel { sql, chartType }` → guard → `SELECT * FROM (…) _panel LIMIT 5001` inside a
  read-only transaction on the `dashboard_reader` pool → `{ columns, rows, truncated }`.
- `POST /api/repair` → one LLM call fixes a failed panel's SQL (frontend retries once, automatically).

Safety: read-only role (`default_transaction_read_only=on`, `statement_timeout=20s`, SELECT-only
grants + per-table RLS policies) → read-only transaction → app-level SQL guard
(`lib/sqlGuard.ts`, tested via `npx tsx scripts/test-sqlguard.ts`) → hard row limit.

Schema context for the LLM is generated by `DATABASE_URL=<admin url> node scripts/introspect-schema.mjs`
into `db/schema-context.md` (committed; routes read it at startup). Re-run it after schema changes.
